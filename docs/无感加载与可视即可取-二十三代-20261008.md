## 三、二十三-2：Lora 600 档晚批查证（B-L）

### 3.1 出处

修复后线上探针读数（二十二代正本 §9.3 备注同源）：`width-live-r23.json`（2026-10-07 17:58Z，
慢窗）字重 loadingdone 分两批——{Lora 400/500/700＋FB NSC 400/500/700} @3815ms、
**{Lora 600＋FB NSC 600} @5116ms**（晚 ~1.3s）。

### 3.2 三源取证（全部无头/同机）

| 证据源                                | 读数                                                                                      | 结论                                          |
| ------------------------------------- | ----------------------------------------------------------------------------------------- | --------------------------------------------- |
| 网络窗（本地 CDP，两档×复跑）         | 四字重请求**同毫秒发出**、7–12ms 全部完成（preload 四字重生效）                           | 网络层已压平，晚批与网络/SW 无关              |
| face 层（document.fonts，本地两档）   | 400 @29ms → {500/700＋FB NSC} @194–248ms → **{600＋FB NSC 600} @646–712ms**               | face **按首用触发**加载，完成序＝首用序       |
| 首个 600 渲染元素（MutationObserver） | `.pref-title`/`.meta-item.stars` 等首个 font-weight:600 有字元素 @**548ms**（首数据提交） | 600 的首个使用点晚于 400/500/700 的启动期使用 |

### 3.3 判定（登记口径，不动）

- **成因＝face 按首用触发加载的固有错峰**：浏览器只在元素首次用到某字面时才持 face 请求
  （preload 只压网络窗）；首启动阶段首用的是 400/500/700，首个 600 元素随首数据提交出现
  → 600 完成恒最后。与 preload 未命中 / SW 缓存交互 / 网络分批**均无关**（网络窗三源已压平
  钉死）。线上 5116ms 的绝对值叠加了当日慢窗（53–75s 波动），不可比、不需修。
- **观感已被既有闸锁死**：换装两侧同度量排版（FB NSC 600 size-adjust 98.11% 按 §9.2 线上
  实测复校）→ 零度量变化换装（W1 零跳变实证）；换装窗量级 ≤8px 一跳上限、>1 跳＝校准
  错档（W2）；四字重漏 preload 即红（W4）。本次取证不改判据、不加闸。
- 附：face 首用触发是平台行为，任何「让 600 不晚到」的手段（手动 `fonts.load("600 …")`）
  只是把 face 请求提前、并不减少已渲染内容的换装面——在零 reflow 前提下无收益，登记后不再追。

## 四、二十三-6：feed.json 到货解析·数据先行（B2 旧）

### 4.1 读数（parse 耗时分布）

| 源                                    | 载荷             | 数据量                                           | JSON.parse ×7                  |
| ------------------------------------- | ---------------- | ------------------------------------------------ | ------------------------------ |
| 本地 dist（headless，2560/1920 双跑） | `data/feed.json` | 4,924,151B / 解析后 3,853,229 字符 / **3420 卡** | **9.1–17.6ms**（两跑合并分布） |
| 线上（Node/V8 同引擎，纯 HTTP）       | 清单 4,930,974B  | **3425 卡**                                      | **11.2–21.7ms**                |

V8 同引擎 → Node 值即 Chrome 主线程 parse 成本侧写。每卡斜率 ≈ **0.003–0.006ms/卡**，
卡量 3.4K→10K 线性外推 parse 仍 <60ms。

### 4.2 决策（数据说话，禁无读数立案）

- B2（旧）的「到货窗 rAF 采样被占 ≈0.9s」里 **parse 占比 ≤2–3%**；主占＝全量到货的 React
  提交＋虚拟列表/网格布局，不是 JSON 解析——把 parse 搬 Worker/流式**收益 <20ms**，
  而新增通道成本（序列化/生命周期/fallback 路径复杂度）远大于收益，与「能不加件就不加件」
  相斥。
- 完整框架的既有硬不变量覆盖到货窗观感：头片冻结序＋零已渲染区重排（H3/W3）——到货窗的
  提交不改动任何已渲染区，「0.9s 占用」期内页面冻结帧是**测量窗属性非行为缺陷**（§八注记）。
- **决策＝不动**，B2（旧）销账；若未来卡量上到万级且合并慢机谱系再复测立项（本条留读数基线）。
