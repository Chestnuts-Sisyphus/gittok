## 〇、问题与偏好（栗子 10-06 原话）

「打开卡片先加载出来其他东西，然后深度解读才闪现，我不喜欢这样，卡片的详情内容应该作为一个整体展现」
＋「整体网站的加载速度和负载等优化也需要做到更好——防负优化只是底线，必须带量化变好」。

提炼（已入记忆）：①内容块**整体呈现**（异步到货补渲＝局部闪现＝设计缺陷）；②每轮带主动变好的量化推进；
③修问题挖类根源＋判据闸化。

旧机制（十九轮止）：点击 → 弹层即时开（09-25 修的响应性，保）→ `feed-details.json`（5.96MB 单文件）
下载完 → `mergeDetail` 补渲 → `FeedCard` 里 `{card.detailCn && (…)}` 条件渲染把「深度解读」区块
**从无到有插入**，下方 meta 被推下＋内容突现＝他看到的闪现。「有时候不闪」＝同日 IndexedDB 缓存命中时
详情即时整体。缺键卡（详情表无此键）连占位都没有＝静默缺失（E2）。

## 一、正解＝数据前移＋占位整体交接（不回退响应性）

### 1. 数据侧：详情表单卡分片（N2② / C3）

- 构建期（vite `prepareFeedPlugin`）：每个 repo 的 `detailCn` 落成独立小文件
  `data/details/<owner>/<name>.json`，内容 `{"detailCn":"…"}`；无长文的卡发墓碑
  `{"detailCn":null}`（确认缺失一次请求有答案，不走兜底）。路径两段**小写规范键**
  （GitHub owner/repo 名大小写不敏感，实测数据有 `Hmbown/Codewhale` 与 `Hmbown/CodeWhale`
  大小写漂移双卡，同 repo 共享同一分片）。构建/运行时路径同源纯函数
  （`payload-split.detailShardPath`），天然一致；落盘有字符白名单＋目录边界校验（fail-closed）。
- 运行时（`feed-payload.ts` 重写）：`resolveRepoDetail(repo)` 四级取数——
  ①会话内存 Map（同步命中 ⇒ 弹层首帧即终态，零交接）→ ②IndexedDB 同日分片缓存（`d:<repo>` 键，
  命中即回＋后台 revalidate 只更新缓存不惊动打开中的弹层）→ ③网络分片（8s 超时）
  → ④整表兜底（legacy `feed-details.json`：分片 404＝部署偏斜或网络失败；one-flight 直拉，
  20s 超时）。每 repo 至多一条在飞（inflight 合流）。
- 语义保全：**boot 零预热不回退**（十二轮 T3：首次点击详情前零请求）；**同日缓存语义不变**
  （日内点击零网络等待）；`feed-details.json` 整表保留（技能/MCP/API.md 的公开接口不动）。
- 实测规模：3404 卡 → 3403 个小写规范分片（含大小写漂移合并），单卡 p50 1703B / p90 2169B /
  max 3357B，合计 5.8MB。分片目录 `.gitignore`（与 feed.json/feed-details.json 同为构建产物）。

### 2. 呈现侧：占位＋整体交接（N1 / C1）

`CardDetail` 的深度解读区改 `DeepReadSlot` 三态槽：

- **pending**：槽位常驻「深度解读」声明位，渲染占位（解读加载中＋脉动点）；
- **ready**：内容整体呈现。经占位交接而来时：`useLayoutEffect` 里把槽从骨架实测高度
  **一次性过渡**到内容实测高度（200ms ease-out，落定归还 auto），内容以 `detail-swap-in`
  （transform+opacity，合成器属性）整体淡入——**至多一次切换、必须带过渡**，禁「先其他后解读」
  分叉突现；首帧即 ready（内存命中/快照卡）＝静态呈现零动画；
- **missing**：显式「暂无深度解读」（灭 E2 静默缺失）。

高度实测在面板飞行 transform 下也准（offsetHeight 是布局值）。App 侧 `detailOpenRepoRef`
守卫迟到的分片响应（换卡/关闭不串写别人的弹层）。

### 3. 字体本地化（N2①，取证后定＝本地化）

旧路径：Google Fonts（preconnect×2 ＋异步 CSS）。线上 trace（10-05 复核册）实测
fonts.googleapis.com 是第三方冷连接域（600–840ms/域），且国内不可达时 Lora **从未真正加载**、
永远系统 serif 兜底——本机冷 profile 探针亦在第三方域清单里见到它。
定案：Lora（拉丁/数字，latin 子集，OFL 授权，文件随 `fonts/LICENSE-OFL.txt` 入仓）改为
**同源随站分发**（`web/public/fonts/*.woff2` ×5 ≈108KB，`index.html` 内联 `@font-face`，
`font-display:swap` 与旧行为一致）：零第三方域、零额外握手、中文栈（系统 Noto Serif SC/宋体）不动。
boot 关键路径零新增（字体仍按需异步取，不 preload）。

### 4. feed.json 分片评估（C3③，结论：**本轮不做**，数据在案）

| 指标 | 实测（2026-10-06，dist 产物，gzip level 6） |
|---|---|
| 列表全量 | raw 4,893,940B ／ gzip 1,361,249B（1.30MB） |
| 前 24 张（首屏窗） | gzip 12,021B（占全量 0.9%） |
| 前 240 张（40 屏×6） | gzip 101,519B（7.5%） |
| 卡均 | gzip ≈400B |

做分片理论上可把冷启动列表载荷 1.30MB → ~12–100KB。**不做**的理由（机制性冲突，非成本借口）：
①频道容量口径是「40 屏×6＝240 张」且推荐/热门/每日都**全池排序**——只喂前缀会给出假 top-240，
喂全量则回到整表；②客户端搜索消费全量语料（3404 卡），分片后要么降级要么全拉；③渐进到货会把
「会话内顺序稳定」（sessionSeed 骨架）变成随加载进度跳变的序；④线上冷 987ms（10-05 实测）
是一次性成本——同日 IndexedDB 缓存让日内刷新全部零网络。若未来重开：先服务端搜索＋频道感知预取，
另行立项。

## 二、判据闸化（C2）

新闸 `scripts/gittok-detail-presentation-check.mjs`（CI presentation job 第 6 步，`pnpm detail:check`）：

- **P0 分片完整性**（管道验证）：每 repo 一个小写规范分片，内容与组内 detailCn/整表对账一致；
- **P1 boot 零详情预热**：点击前 details 类请求 = 0；
- **P2 响应性不回退**：点击 → 弹层在场 <100ms（五轮 T1 锁的行为级化）；
- **P3 占位先行**：分片被闸延迟 600ms 时，弹层开而详情未到＝「解读加载中」占位在场、内容缺席；
- **P4 整体交接**：占位→内容**恰一次**、带 `detail-swap-in` 过渡、落定槽高=内容高（无推挤残差）；
- **P5 缓存命中零交接**：同卡二开首帧即内容、全程无占位闪过；
- **P6 缺键显式「暂无」**：无分片卡（闸注入）→ 显式空态、永不伪造内容；
- **P7 韧性**：分片全 500 → 弹层仍 <100ms，内容经整表兜底最终在场。

配套：motion 闸补 `document.fonts.ready` 前置（字体换装的一次性重排不属运动判据管辖区，
否则随机假红）。缺键卡定位通道用**搜索**（推荐/热门有会话抖动 ±9%，注入卡不保证进首窗）。

## 三、意外收获：搜索页白屏（既有生产 bug，一并根治）

构建新闸时发现：点「搜索」标签 → React error #185（Maximum update depth exceeded）→
**整棵 App 卸载、整页白屏**。**线上旧 bundle 同样复现**（本机 headless 冷 profile 实测），
与本轮改动无关、先于本轮存在。
根因（dev 模式组件栈实锤）：`useResponsiveCols` 的 ref 是**内联箭头**（每渲染换身份 → React
每渲染重挂 → 重挂即 measure → `setShape` 每次新对象永不 bail → 再渲染）——在搜索空态这种
内联渲染子树里打满嵌套更新上限。主信息流不炸只因 ref 消费者被 memo 挡住（同一颗雷全站埋着）。
修法：ref `useCallback` 稳定化＋`shallowEqShape` 逐字段 bail（App.tsx），回归锁
`web/src/__tests__/responsive-cols-loop.test.ts`（源码级，谁把内联箭头/无 bail 加回来谁红）。
