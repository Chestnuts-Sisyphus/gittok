# 乐趣判据 v1 · 从「一句话定义」到「可复现判据体系」（2026-09-14 晚）

> 栗子原话：「现在的乐趣分区不够乐趣，你得**从底层拆解**到底什么样的项目人们看到会觉得乐趣，
> 这很关键」。
>
> 结论先说：**问题不在阈值，在判据**。v2.2 的 fun_score 定义是一句话
> 「0=纯工具、1=极好玩（游戏/脑洞/创意玩具）」，实测退化成**「游戏 / AI-Agent 探测器」**
> ——全库 234 张 ≥0.9 的卡里绝大多数是游戏或 AI Agent；同时判定输入只有 160 字摘要
> （`detailCn` 全文与 README 都没进模型）。三件都不足以支撑「乐趣」，所以怎么调阈值都不会有趣。

---

## 一、v2.2 的三处硬伤（已实测）

| 项 | 实测 |
|---|---|
| 判据只有一句话 | 生产 prompt 对 fun_score 的全部定义 = 「让人想点开玩的冲动强度……眼前一亮/想玩/忍不住点开的直觉强度」——**没有拆解「为什么会有这种冲动」** |
| 判定输入贫瘠 | 回填脚本 `buildPrompt` 用 `(summaryCn ?? reasonCn ?? desc).slice(0, 160)`——**只喂 160 字摘要**，detailCn（几百字）与 README 全都没进模型 |
| 无金标准 / 无反馈 | 全库没有任何「栗子认定有趣」的锚点样本；点赞/点踩/收藏**不回写** funScore（只进 localStorage 当推荐权重）→ 判据对不对无从验证，也永远学不到口味 |
| 退化的证据 | funScore ≥ 0.9 的 234 张里，创意区（游戏/绘画）占绝大多数；AI Agent 类项目普遍 0.7-0.9（「是 AI」被当成了「好玩」） |
| F3 隐蔽问题 | 乐趣池 top60 与 top200 门槛**同为 0.9**（满分 1.0）→ 高分段极稀，放开容量也填不满 |

## 二、v1 判据：六维拆解 + 合成公式

把「想点开玩的冲动」拆成**六个可以分别判定**的成分（每维独立判 0 / 0.5 / 1，拿不准则给 0）：

| 维 | 中文 | 判什么 | 不算的情形 |
|---|---|---|---|
| `surprise` | 意外感 | 读到一半会不会「哎？还能这样」——反直觉、意料之外、把不搭界的东西接在一起 | 只是功能多；只是别人也这么做过的常规做法 |
| `play` | 可玩性 | 能不能立刻上手玩、有交互、点一下就有反应 | 要写代码/配环境半天才看到东西；只是把数据画成图表 |
| `wow` | 奇观 | 视觉或规模上有没有冲击力（一眼惊艳的 demo、极致渲染、硬件奇观） | 朴素的后台界面；只是架构漂亮但看不见 |
| `absurd` | 荒诞 | 有没有脑洞 / 整活 / 幽默——一本正经地做荒唐事 | 正经工程；只是名字起得怪 |
| `voice` | 表达欲 | 作者是不是在皮、在表达自己（彩蛋、梗、有个性的文案） | 标准企业开源项目的正经语气 |
| `rarity` | 稀缺性 | 会不会让人想「居然有人做了这个」——前人没做过、极小众、偏执到极致 | 同类一大堆的又一个实现 |

**合成公式**：`fun_score = 六维最大值 + 0.1 ×（≥0.5 的维度个数 − 1）`，封顶 1.0；六维全 < 0.5 → 整卡 0。

- 取 `max` 打底：**单点极强的卡不吃亏**（纯奇观、纯荒诞也能拿高分），避免维度互相稀释；
- 命中维度数加成：多点皆中的卡额外加分，防止「哪一维都不突出」被平均掉；
- 公式与六维定义都在 `src/feed/taxonomy.ts`（`FUN_DIMS` / `funFromDims` / `FUN_RULES_V3`），
  **本地按公式算**，不信模型自己报的算术。

### 硬性反污染纪律（写进 prompt，针对 v2.2 的退化）

- **题材不加分**：项目是 AI / 模型 / Agent、或者话题很热，本身不构成任何一维；
- **「是个游戏」不加分**：只按「可玩性」看它好不好上手，无聊的商业复刻 = 0.5，其余全 0；
- **正经生产力工具 / 框架 / 数据库 / 运维面板**：六维全 0，不要因为「做得用心」给分；
- 打分对象是**卡上写的内容**（含详情全文），不是项目的名气或星数。

## 三、输入升级（B2，判据的必要条件）

判定输入从「160 字摘要」升级为：

```
repo ｜ 语言 ｜ 星数 ｜ 建仓时间
描述：desc（≤200 字）
话题：topics（≤8 个）
一句话：summaryCn（≤120 字）
简介：reasonCn（≤220 字）
详情全文：detailCn（≤900 字）      ← v2.2 完全没有这一项
```

实现在 `scripts/gittok-rejudge-v3.ts` 的 `buildPrompt`；生产侧 `src/feed/prompts.ts` 本来就有
README 输入块（`buildProjectBlock`），两边口径即「内容资产全量进判据」。

## 四、金标准锚点集（B3）

文件：`data/fun-anchors.json`（**改这里不用改代码**）。本轮提案 **76 张**：正锚点 35 + 负锚点 41。

- 正锚点：可玩性强的游戏本体、脑洞整活、奇观 demo、纯表达欲小玩意（含 18 张「难例」——
  看起来像正经工具其实很妙，例如「把你变成操作系统调度器的游戏」「用 WiFi 信号感知房间里有没有人」）；
- 负锚点：基础设施 / 框架 / 数据库 / 清单读物，**外加 22 张难例**——「看起来很好玩其实不是」：
  游戏引擎（LayaAir / sbox-public）、游戏 AI 库（yuka）、UE5 插件、把「炫酷」写在描述里的
  可视化库（antvis/L7 / plotly.js）、提示词泄漏合集（system_prompts_leaks）、
  开源游戏清单（open-source-games）——**这些正是 v2.2 误判 0.8-1.0 的那批**。

复现口径（`scripts/gittok-fun-anchor-check.ts`）：
- 正锚点复现 = `funScore ≥ 0.7`；负锚点复现 = `funScore ≤ 0.3`；
- 落在 0.3-0.7 中间地带：既不算命中也不算失败（判据没表态）；
- 验收线：复现率 ≥ 85%，并单独报**难例复现率**（普通样本猜对不算本事）。

**修前基线（v2.2 判据，实测）**：复现率 **69.7%**（53/76），难例 **50.0%**（20/40），
12 条错判全是难例负锚点（diffusers / gemini-cli / eliza / system-prompts / magictools /
open-source-games / LayaAir / sbox-public / yuka / InstantOrganicCaves / L7）。
**修后数字见验收报告**（判据换 v3 后重跑同一份锚点集）。

> 锚点集是**提案**：栗子删改增补后即为定稿。改法——直接编辑 `data/fun-anchors.json`
> 的 `anchors` 数组（`label: pos|neg`、`hard: true|false`、`why` 写理由），跑
> `npx tsx scripts/gittok-fun-anchor-check.ts` 即可看到新复现率。

## 五、反馈闭环与乐趣频道体验（B4 / B5 / B6 / F3）

| 项 | 做法 | 位置 |
|---|---|---|
| 反馈回写 | 点赞 +0.15 / 收藏 +0.1 / 点踩 −0.3（不对称：错判比漏判更烦人），排序前叠加并夹到 [0,1]；**不改数据文件** | `web/src/feedback-score.ts` + App.tsx 乐趣分支 |
| 云端回写 | **未做**：站点是 GitHub Pages 静态站，没有后端可写；要上云端得先有账号体系（产品决策） | — |
| 与创意解耦 | 全靠新判据把「AI 题材 / 游戏题材」的虚假高分清掉（重叠率目标 <35%） | 见验收报告标定 |
| 多样性配额 | 乐趣频道两级：创意 ≤40% 前缀配额 + **同 domainKey ≤ max(3, 15%×前缀)**（防同族霸榜） | `channel-policy.ts` 的 `funChannel` / `interleaveByCountCap` |
| F3（top 门槛 0.9） | 池子口径改为 `funScore > 0`（六维判据下「正经工具 = 0」，所以 >0 = 至少命中一维） | `channel-policy.ts` 的 `funChannel` |

## 六、关键假设（未说明处按推测执行，栗子扫一眼可纠偏）

1. **六维权重**：取「max + 命中数加成」而不是加权求和——理由见 §二（单点极强的卡不该被稀释）。
   若栗子想改成加权，改 `funFromDims` 一处即可（六维定义不变）。
2. **反馈增量幅度**（0.15 / 0.1 / −0.3）是我拍的：单次互动不掀翻大秩序，多次互动才翻。
3. **乐趣池口径 = funScore > 0**：而不是 ≥0.5。含义是「至少命中一维就算进池，排在末尾」，与
   「频道容量无限、真实张数」的产品口径一致（栗子：不能告诉用户这个频道只有 60 张）。
4. **锚点集正负比 35:41**：负锚点刻意多于正锚点且难例占一半——因为 v2.2 的失败模式是
   **误判高**（把不好玩的判成好玩），而不是漏判。
