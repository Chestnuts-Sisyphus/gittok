## 一、背景与改判（为什么有这一轮）

栗子 10-07 判定：「之前说的问题都没解决」。拆开是两件事：

1. **迁移面**：他的屏幕可能还跑旧 bundle（HTTP 缓存 600s＋常驻标签页）。SW（二十一轮已上线，
   network-first＋skipWaiting＋claim）已保证此后每次部署即时到达，迁移窗内硬刷新一次即闭环
   （一次性成本，真机有头对线上已实证新 bundle 四条全过）。
2. **冷路径加载可感＝真未解决**：feed.json 仍占冷首载 91%（1.2MB gzip 级）。二十一轮的
   「数据否决」否掉的是**朴素热替换方案**（头片池 n≠全量池 n ⇒ 热替换必重排：head-192 实测
   18/24 成员变动＋24/24 位次错位），**不是诉求本身**。诉求（「无法感知加载」）还开着。

本轮以**冻结式头片**闭环诉求：头片不是「先渲染一半再替换」，而是**它本身就是会话序的头部**。

## 二、冻结式头片设计（二十二-0，P0）

### 2.1 机制

- **构建期**：`vite prepareFeedPlugin` 用与运行时**同一份排序实现**（`web/src/recommend-baseline.ts`
  的 `buildRecommended`，App.tsx 原位迁出、双端 import——防「前后端两套排序」的 L8 事故复刻）
  以默认个性化参数（无偏好/无已读/无互动/无关注）算出推荐频道 baseline 序，取 top-256 发射为
  `data/feed-head.json`。
- **冷启动**（无同日 IndexedDB 全量缓存）：先取头片（gzip 107.0KB）即时渲染推荐频道；
  头片 TTFB 3s 闸，失败静默退回「等全量」旧行为（它是加速件不是必需件）。
  顺序取数是有意的：头片独享带宽窗口先到（五轮 T1 教训：大小件并行小件饿死），全量随后后台走完
  主源/镜像链。
- **全量到货**：推荐频道定序＝**头片冻结序 ＋ 尾部 append**（尾部＝全量会话序剔除头片成员后的
  相对序，按 repo 去重保证每张卡恰好出现一次），与 `setCards` 同一批 React 提交——不存在
  「先按全量重排、再冻结」的中间帧。已渲染区从此不再随任何数据事件变动。
- **定序生命周期**：用户改偏好/关注＝用户动作，解除冻结回到原重算管线（与暖路径行为一致）；
  数据到货**永不**自动解除。
- **冷窗（头片已渲染、全量未到）**：其他频道与搜索保持加载态，不渲染残缺序（闸 H5 锁）。

### 2.2 硬不变量（为字节让步此不变量的方案不许上）

**全量到货零已渲染区重排（会话内定序字面保全）**——闸 H3 逐帧探针：rAF 采样视口指纹
（可视卡 `data-repo@offsetTop` 序列），从到货前 1s 起单一指纹**横跨到货时刻**直到落定
（本轮实测 207 帧一态横跨，零位移）。

### 2.3 为什么 22 位的「洗牌」问题不复现

二十一轮否决的机制：会话洗牌骨架 `(2−idx/n)` 依赖池规模 n，切片洗牌≠全量洗牌切片。
本设计**不洗头片**：头片在构建期以 baseline 序冻结；运行时冷窗直接按头片序渲染；
尾部来自全量管线但**只 append 不插队**。洗牌漂移读数（head-eval 探针，5 种子）：
baseline top-256 与洗牌后 top-256 成员变动 35–38 张、前 24 位次最大位移 162——这些差异
不再表现为「重排」，而表现为**软化①**的接缝次序（见 §三）。

## 三、两处软化（如实登记，待栗子追认；不静默）

1. **seam 处 prefix-quota 短暂失守**：头片尾部与 append 尾部的接缝（第 256 张前后一小段），
   配额节律可能短暂偏离（头片是 baseline 序、尾部来自带洗牌的全量序；接缝处四区交错可能
   出现短同区段）。头片内部与尾部内部各自满足配额性质。首屏两行（前 12 张）实测四区序列
   `AI AI 工具 AI×8 工具`（AI 席偏多属 pagedQuotaMerge 补席机制的正常输出，与主站一致）。
2. **回访者（IndexedDB 过期但有偏好/已读）冷首屏个性化深度受限**：冷窗渲染 baseline 序
   （不按其偏好重排——重排会让「冻结」失去意义且与尾部接缝更差）；其点踩过滤（applyFilter）
   仍然生效，只是偏好配额要到全量到货才体现。**首访者（无偏好）零软化**：无偏好时
   baseline 序＝个性化序。

## 四、预取覆盖面补全（二十二-1，P0）

`FeedVirtualList` 的窗口驱动预取只覆盖走虚拟列表的卡面。三处**直接 markup**卡面原先
点击只能走占位竞态（与可视即可取 P0 冲突——他点收藏夹/创作者页会看到「解读加载中」）：

| 卡面             | 位置                         | 通道                                                       |
| ---------------- | ---------------------------- | ---------------------------------------------------------- |
| 收藏夹展开网格   | 我的-收藏（App 直接 markup） | `useIdleDetailPrefetch(expandedFolderRepos)`，仅夹子展开时 |
| 创作者页         | `CreatorPage.tsx`            | `useIdleDetailPrefetch(projects.map(…))`，组件挂载即预取   |
| 搜索空态热门预览 | 搜索 tab 空 query            | `useIdleDetailPrefetch(hotPreview…)`，仅搜索空态时         |

通用通道 `web/src/use-idle-prefetch.ts`：与虚拟列表同一个 `requestIdleCallback` 调度
（无观察器 API，open-regression 锁兼容）、同一份内存合流；不可见面传空数组＝零请求
（detail 闸 P1「预取 ⊆ 可视卡集合」同样约束这些卡面）。闸 P10–P12 三处各点击一可视卡：
弹层 <100ms 且首采样即内容。

## 五、投毒防护（二十二-2，P0）

**缺陷机制**：预取期间网络瞬断 → `resolveRepoDetail` 把 null 落会话内存（网络失败与
「确认缺失」同型）→ 该会话内点击这些可视卡恒显「暂无」，网络恢复也不重试。二十轮点击路径
同病但爆炸半径=单卡；预取把它放大到全部可视卡。

**修法（失败语义分离）**：

- 网络失败＝**未知**：`resolveRepoDetail` 失败路径不落内存（Promise 拒绝），下次点击/预取重试；
  整表取数失败**抛错**，不再伪造 `"{}"`（旧版 catch→"{}" 把网络失败伪装成空表→键缺席→确认缺失，
  是投毒上游）。
- 确认缺失＝**null**：分片墓碑（`{"detailCn":null}`）/整表核对无键，落内存，首帧即「暂无」。
- 点击路径：占位保持＋有界退避重试（3 次×1.5s）；重试耗尽保持占位（关掉重开＝新尝试），
  「暂无」只属于确认缺失。

闸 P13：分片＋整表全 500 的预取窗 → 弹层即时、深度解读槽=占位（不是「暂无」）→ 恢复 200 →
重试链路取到内容 → 重开同卡首采样即内容（内存终态干净）。

## 六、legacy 兜底阻塞类根源（二十二-3，P1）

**缺陷机制**：缺键/部署偏斜兜底路径解析 5.9MB 整表（`JSON.parse`）在主线程 50–250ms，
排在点击渲染前（CI P6 257ms 假红的直接原因；二十一轮只做了「闸里等落定」的症状修正）。

**修法**：解析搬进 Worker（`web/src/legacy-table-worker.ts`，主线程只发文本收结果；Worker 内
缓存上次解析的表，同日文本不变＝后续查询零重解析；构造失败自动退回主线程解析，兜底语义不变）。
闸 P9：缺键卡点击路径（PerformanceObserver 采样）零 >50ms 长任务；P6 的落定等待
1500→500ms 仍绿（免等待达标的闸上证据，口径未放宽）。

## 九、二十三代 N3b：主页宽度跳变根修（2026-10-07 晚追加）

### 9.1 归因（线上真机探针，三源交叉）

栗子复验报告：「有时候点开主页还是会出现自动的宽度变化导致的观感问题」。二十一轮的
「零跳变」实证只闭合了 **400 字重域**（只 preload 400；宽度时间线闸窗 9s）。二十三代
探针 `gt-r23/width-live-r23.mjs` 对**线上**冷 profile 拉长采样窗重跑，复现唯一一跳，
三源交叉钉死：

| 证据源   | 读数                                                                                    | 结论                        |
| -------- | --------------------------------------------------------------------------------------- | --------------------------- |
| 时刻对账 | 跳变 @1565ms；Lora 600 批次 loadingdone @1546ms（其余字重 @983/@21ms）                  | 跳变＝600 档换装窗（±20ms） |
| 量级对账 | 旧 size-adjust(600)=95.24%（二十轮本机写死）vs 线上实测 98.11% → +2.87pp×300px≈**+5px** | 观测跳变 295→300 恰为 +5px  |
| 机制对账 | 二十一轮 preload 只有 400 一档 ⇒ 500/600/700 走 font-display:swap **异步晚到换装**      | 慢字重换装落在已渲染卡上    |

另查明：`Lora/NSC 宽度比`同字重串间漂移 ≈1pp（4 串实测 93.38–99.35%），**size-adjust
单标量机制性不可绝对零差**——它只是把误差压到 px 级以下的近似件，兜底校准一旦错档
（600 档差 2.87pp）就现形。

### 9.2 修复（三层）

1. **Lora 400/500/600/700 四字重全部 preload**（`index.html`；换装窗统一压到字体早期
   窗口；fonts/ 已全入 SW 预缓存，二访 0 网络；italic 用点=0 不消耗预算）。
2. **FB NSC 四档 size-adjust 按线上实测中位重写**：400:94.92%（原 96.25%，残差 1.33pp）／
   500:96.13%／**600:98.11%（原 95.24%，错档 2.87pp＝跳变直接来源）**／700:96.38%。
   TNR 族本机未变暂不动（无 NSC 机器才走 TNR 族，同法可复校）。
3. **新闸 `scripts/gittok-width-freeze-check.mjs` 4 判据进 CI**：W1 fonts loaded 后
   四 slot（body.scrollWidth/latin 基准串/feed-col 宽/卡宽）零跳变；W2 换装窗至多一跳
   且 ≤8px（度量交接单帧，>1 跳/>8px=兜底校准错档）；W3 feed.json 到货 ±1s 零宽度跳变
   （冻结式头片姊妹不变量）；W4 Lora 四字重全部注册（防漏 preload 复活）。

- **纪律（当夜新增）**：一切探针一律 headless 或纯 HTTP；有头浏览器＝弹窗级打扰（栗子
  2026-10-07 当场叫停）。

### 9.4 同类覆盖（举一反三）

- 换装跳变类：任何新增 @font-face 字档必须**同批 preload**（W4 闸锁），不许出现
  「部分字重早到、部分晚到」的双源渲染窗。
- 数据到货宽度类：W3 把「数据到货不改任何已渲染盒宽」闸化——与冻结式头片的
  「零已渲染区重排」（H3 逐帧指纹）互补：H3 管视口内容位移，W3 管盒宽。
- 兜底校准类：size-adjust 是近似件不是事实件；任何写死值必须带「实测来源＋机器环境」
  登记（本文件 §9.2 即口径），换字体/换环境必须复校（探针 `gt-r23/font-recheck-live.mjs`）。

### 9.5 二次报案根修：tab 切换宽度变化（N3b-2，2026-10-08 凌晨）

栗子二次复测报案：「点首页、点我的的时候还是会有宽度变化的动画」——「动画」＝多帧渐变
观感，与换装单跳不同型，指向另一机制。无头探针（`gt-r23/tabs-geometry.mjs`）取证：

| 档位      | 首页（壳内居中）                 | 我的（无壳贴左）                       | 切换后果                                |
| --------- | -------------------------------- | -------------------------------------- | --------------------------------------- |
| 2560×1440 | 外壳 x=334/宽 1866，内容区 x=550 | 外壳 x=0/宽 2534（满幅），内容区 x=216 | **内容块水平跳 334px＋右侧 668px 空档** |
| 1920×1080 | 外壳 x=14，内容区 x=230          | 外壳 x=0，内容区 x=216                 | 跳 14px（可见）                         |

**真实根因＝2026-09-23 的「超宽屏整壳居中」轮只给 `.feed-layout` 加了壳、漏了 `.me-layout`**
——同轮意图是「侧栏＋内容整壳居中」，me tab 没跟上：`Lora/NSC 宽度比`之外的第二处
「宽度变化」来源。gutter 恒 8（`scrollbar-gutter: stable` 既有件已覆盖滚动条假设，排除）。

**修复**：`.me-layout` 与 `.feed-layout` 同算式同壳（`max-width: calc(var(--max-width)+216px);
margin: 0 auto`）。修复后探针：2560/1920 两档切换 contX 单值零变化；width 闸升 5 判据
（新 **W5：首页↔我的外壳/内容区 x/width 逐位一致**）进 CI。全闸复绿（width 5/5·detail
16/16·head-freeze 7/7·SW 4/4·responsive 480·drag 26·smooth 13·motion 19·visual 全 PASS·
vitest 631）。

**同类登记（本轮不动，下轮按同法收）**：agent/搜索 tab 走 `.main` 自身 1650 居中，与
feed 壳内内容区（1650 但偏右 216）在宽视口下存在水平位置差——属「tab 切换几何」同类，
