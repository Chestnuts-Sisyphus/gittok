# 存量卡为什么永不过闸：机制边界与最小改动方案（G-03 / COPY-05）

生成：2026-09-19（Qoder）｜取证：逐行读 `src/feed/index.ts` + 实跑 `scripts/gittok-copy-audit.ts`
结论：`cardChecks` 只判「LLM 当轮新返回的打分结果」，历史卡从缓存白名单原样回灌，**代码路径上不存在复检点**。

## 三处关键调用点

| 位置 | 干什么 | 是否判存量卡 |
|---|---|---|
| `src/feed/index.ts:613-643`（`loadExistingScores`） | 读 `data/feed.json` 建 `scores` Map：凡 `reasonCn && aiScore!==undefined` 的卡，按**字段白名单**原样装回 `ScoringResult`（zone/zoneSource/funScore/funDims/tags/domainTags→tags/summaryCn/reasonCn/detailCn/facts…） | **否**，无任何 `cardChecks` 调用 |
| `src/feed/index.ts:1018`（`retryScoring`，起于 `:980`，逐仓带反馈重评） | `parseScoringResult(raw)` 出的**新** `sc` 过 `cardChecks(sc, doc)`，不过 → 带反馈重试 ≤3 次 | 只判这一轮重新打分出来的卡 |
| `src/feed/index.ts:1401`（批量装配主循环） | 同上：`cardChecks(sc, doc)` 的入参 `sc` 来自本轮 LLM 返回；`:1370` 的 `cachedHit` 分支直接 `existingScores` 回灌 | 只判新打分卡 |

回灌后的 `existingScores` 在 `:1357` 被并入结果集，最终 `:1663` `fs.writeFileSync(FEED_PATH, final)` 落盘——**中间没有任何一道文案闸**。CI 侧同样只有结构闸（`.github/workflows/ci.yml:44` card-invariants）与容量闸（`:49` channel-capacity），文案闸一次都没跑（COPY-06）。

所以「67.6% 存量卡不合规」不是闸失效，而是**闸的覆盖面从来只有新增卡**：现行全库真实合格率 870/2682 = 32.4%。

## 复检需要哪些字段（照 `gittok-recopy.ts:135-149` 的 `gateOf` 口径）

`repo` / `zone` / `funScore` / **`domainTags`（不是卡上的 `tags`，那是 Tag 对象，喂进去 `validateScoringResult` 会抛错）** / `facts`（缺键即整段 facts 闸跳过，见 COPY-04）/ `summaryCn` / `reasonCn` / `detailCn`（`index.html` 走拆表时要能从 `feed-details.json` 回退取）。G9（批内开头 LCS）需要**同批多卡**同时在场，逐卡复检做不了，属批次级判据。

## 最小改动方案（**本文件只是方案，未落地**）

在 `:1663` 写盘前加一段全库复检：对 `final` 逐卡跑 `cardChecks`，`console.warn` 汇总「不合格 N 张 / 占比 / TOP 10 repo」，**不改写任何卡、不改退出码、不剔出推荐池**（呈现策略属 COPY-08 等裁）。实现上直接把 `scripts/gittok-copy-audit.ts` 的逐卡判定抽成导出的纯函数复用，避免第二套判据。落地点需栗子点头：一是生产装配链（动一次全站数据），二是与「不合格卡不上站」这条既有纪律的关系（现状是违背它还是只报警）。
