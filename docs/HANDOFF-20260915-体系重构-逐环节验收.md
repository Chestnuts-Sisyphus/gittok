## 一、V-C 频道容量与浏览深度（栗子 L8「这几个频道都只有 60 个」）【已实测】

复跑：`npx tsx scripts/gittok-channel-capacity.ts`（数据源 data/feed.json；CI 已接同一脚本）

| 频道 | 修前可见 | 修后可达 | 重复 | 前缀配额违规 |
|---|---|---|---|---|
| 热门 | 60 / 418（14.4%） | **418** | 0 | 0 |
| 每日 | 60 | **256** | 0 | — |
| 乐趣 | 60 / 940（6.4%） | **2462**（v3 判据落库后会收窄，见 §三） | 0 | 0 |
| 关注 | 60 | **2477**（全量看到） | 0 | — |
| 分区 AI / 资源 / 工具 / 创意 | 60 | **576 / 230 / 1206 / 465**（整区） | 0 | — |

- **单一事实源**：容量与配额只在 `channel-policy.ts` 定义一次，前端 `App.tsx` 与后端 `channels.ts` 都 import；
  v2.2 的四处硬编码 `60`（前端 getSectionCards ×4 + 后端默认参数 ×3）**已删除**（源码里搜不到 `limit = 60`）。
- **容量语义**：`CHANNEL_CAP = Infinity`（栗子拍板「我需要的是无限」）；`CHANNEL_PAGE_SIZE = 60` 只表示
  「每批渲染/增量加载张数」，与容量脱钩——v2.2 的 bug 正是把两者混成了一个数。
- **左上角真实张数**（栗子：「不能告诉用户这个频道只有 60 张，这是欺骗」）：频道头改为
  `共 N 张 · <频道说明>`，N = 该频道池子真实长度（`channelPoolSize` 与频道函数同口径，测试锁死
  「显示张数 = 实际输出张数」）；推荐频道也显示（原先推荐没有频道头）。
- **浏览到底**：虚拟列表按视口渲染（已有 `feedWindow`），容量放开后滚到底即池子见底，
  底部提示「已加载全部 N 个项目」。
- **池子容量 vs LLM 评分窗口的关系（任务书 G-C 第 ④ 项，防「池子只有 60」的假象）**：
  两者是**完全不同的量**，v2.2 把「每批渲染 60」误当成了「池子上限」，所以要先说清：
  | 量 | 取值 | 作用域 | 代码位置 |
  |---|---|---|---|
  | `MAX_LLM_SCORE_REPOS`（= `SCREEN_CAP`，默认 3000） | 每轮**海选**（phase1 打分）的候选上限 | 生产管道每轮的工作量闸，只影响「哪些库本轮能进评分队列」 | `src/feed/index.ts:76` |
  | `PROSE_TOP_K`（默认 400） | 每轮**精评**（写全文案）的 top-K | 每轮新增完整卡产量旋钮 | `src/feed/index.ts:81` |
  | `CHANNEL_CAP`（= `Infinity`） | **频道展示容量** | 前端/频道函数，**不是**入库闸 | `src/feed/channel-policy.ts` |
  即：**频道能滚到多少张，只取决于「已入库且通过该频道过滤的卡有多少」**（实测热门 418、乐趣 447、全库 2537），
  与上面两个 LLM 闸无关——那两个闸决定的是「库有多快长」，不是「频道有多长」。
  所以看到频道显示「共 N 张」时，N 就是真实可滚张数，不存在「后台其实只有 60」的隐藏上限。

- **配额实现换代**：v2.2 的「按席位挑选」会**丢卡**（放开容量后整段砍尾巴），换成
  **前缀配额交错**（`interleaveByCap`）：输出是输入的排列（不重不漏）+ 任意前缀满足占比上限
  （热门/每日 AI ≤30%、乐趣 创意 ≤40%）。数学边界在代码注释里写明：池子本身某分区占比超上限时，
  超额部分只能退到尾部（仍可见、不丢）。

## 二、V-A1 分区体系正交性（栗子 L10「问题在于分类体系本身」）【已实测 + 待跑完】

复跑：`npx tsx scripts/gittok-zone-orthogonality.ts`

**体系结构**（构造性互斥，不是抽查结论）：

```
问 1 它是「作品」吗？（玩/看/听/自己动手创作）        答是 → 创意
问 2 它是「读物」吗？（不安装不运行，读/下载就拿全价值） 答是 → 资源
问 3 它是「智能本体」吗？（拿掉 AI/模型什么都不剩）    答是 → AI
三问全否                                              → 工具（兜底）
```

排他性由构造保证：工具区的条件是「三问全否」，因此工具区的卡**在定义上**不可能属于其余三区
（栗子：「工具里的任何一个项目拉出来都不可能成为其他三个分区的内容」）。

**判例集**（写进 prompt、脚本与文档）：skill 包 → AI（栗子点名的错分，在此闭死）；AI 教程/清单 → 资源；
AI 绘画工作台 → 创意；Agent 框架/推理引擎 → AI；游戏引擎/开发框架 → 工具；带 AI 摘要的自托管笔记 → 工具。

**数据层（待重判跑完填最终值）**：完备 100%、均衡无单区 >60%、稳定（抽样 100 张重判改动率 ≤15%）。
v2.2 基线（本轮修前）：工具区 1206/2477 = **48.7%**（擦线），其中 402 张（33.3%）描述带 AI/模型/Agent 关键词。

**A3（四处耦合）**：zone 词表与 category 映射收敛到 `taxonomy.ts`；前端 tab 词表、后端频道函数、
生产 prompt、回填脚本、验收脚本全部 import 同一份。
**A4（zoneToCategory 往返丢语义）**：v3 下不再成立——四区枚举未变，`category ↔ zone` 是 **4↔4 双射**
（脚本对双射性加断言），且新增 `legacyZone` 承载旧值，不再需要用「压回旧 category」表达新语义。
