## 四、顺带查实的一个真 bug（非判据问题，建议尽快修）

`src/providers/openrouter.ts:49`：

```ts
const text = response.choices[0]?.message?.content;
```

`?.` 只护住了 `choices[0]`，**没护住 `choices` 本身**。OpenRouter 在限流/错误时可能回一个
没有 `choices` 字段的 JSON（HTTP 200 + `{error:...}`），于是 `undefined[0]` 直接抛
`TypeError: Cannot read properties of undefined (reading '0')`——这把"通道限流"误报成"代码异常"，
既污染失败原因，也让 `lane-health` 记不进正确的 429 计数。

- 现象实证：`anywhere-labs/dsh-desktop` 的 state 条目；
- 一行修法（**本次未改，等栗子点头**）：`response.choices?.[0]?.message?.content`；
- 影响面：不止这一张卡——所有走 OpenRouter 的调用在异常响应下都会走到这个 TypeError。

## 五、疑似判据误伤（**本次一字未改**，按硬约束"不擅自改判据"上报）

`yt-dlp/yt-dlp` 的失败原因是「含推广词『赞助』（禁止）」。yt-dlp 的 README 本身就有
sponsor/赞助段落，模型**如实复述源文档**时就会命中禁词。

- 这是"禁词表拦的是**模型自己加的推广**"还是"**源文档里本来就有的词**"的边界问题；
- 若是后者，则该卡在现判据下**恒不过闸**（与模型强弱无关）；
- 处置建议（三选一，**等栗子勾**）：
  1. 维持原判 → 该卡按"宁缺毋滥"不上站（不动判据）；
  2. 禁词校验改为"仅当该词不出现在参考文档中才判失败"（判据改动，需重判影响面评估）；
  3. 人工为该卡放行一次。
