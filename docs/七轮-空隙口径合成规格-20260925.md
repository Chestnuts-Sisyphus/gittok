## 一、规则（一条，可直接复算）

```
列数 n = max{ n : (W − (n−1)·16) / n ≥ 653 }        # W = 内容网格宽；653 = 一行放得下 35 字
卡宽   = n === 1 ? min(W, 793) : (W − (n−1)·16) / n  # 与 feed-layout.ts feedCardWidthFor() 同式
理由行数 = clamp(ceil(150 / floor((卡宽 − 69) / 13.94)), 3, 4)   # 见第三节
轨道留白 = W − 卡宽（单列档 = W − 793，**对称**分在两侧：justify-content: center）
```

- **轨道里不留空**（卡宽 = 轨道宽）——09-24 栗子红框那条继续成立；
- **轨道之外**的余量 = 对称页边距，**不左对齐、不单侧留**（左对齐是栗子 09-24 明确否掉的形态）；
- 三处同真：`web/src/feed-layout.ts`（推导）·`web/src/styles.css`（`--feed-card-max` /
  `--feed-reason-lines`）·`scripts/gittok-responsive-check.mjs`（R1/R4/R5 判据），由 lock 单测钉住。

## 二、为什么中间带一定有留白（三条口径互斥的证明）

设内容网格宽 W。历史三条口径：① 卡宽 ≤ 793（09-25 栗子）；② 单列不许大块空档（09-24 栗子）；
③ 内容契约不得截断（摘要 20–35 字一行、理由 100–150 字；〇块第 7 条「内容契约优先于版式」）。

- 由 ③ 反推卡宽的**允许区间**：摘要一行放 35 字 ⇒ 卡宽 ≥ 653；理由 3 行放 150 字 ⇒ 卡宽 ≥ 766。
  两列档每列卡宽 = (W−16)/2，单列档卡宽 = min(W, 793)。
- **W ∈ (793, 1322)**（＝视口 ≈1065–1594，覆盖 1366/1440/1500/1536 这些常见窗口）时：
  - 走 1 列 ⇒ 卡宽 = 793 ⇒ 余量 W−793 = 0…528px，**必然**成为留白（② 破）；
  - 走 2 列 ⇒ 卡宽 = (W−16)/2 = 389…653 < 653 ⇒ **摘要与理由都被截**（③ 破，实测见表）；
  - 取消上限 ⇒ 卡宽 = W = 794…1321 ⇒ 栗子 09-25 明确否掉的「太长了」（① 破，1600px 那张卡的原话）。
    ⇒ **三条不可同时成立**；本轮取 ①+③（内容优先），放弃 ② 的「中间带零留白」。

## 三、同轮修掉的那个**真**缺陷：理由行数写死 3 行

# 八轮追加（2026-09-25 晚）—— 栗子给定版口径（本规格的最终规则）

## 一、栗子的两条指令（原话）

1. 「**首先不允许出现留白**，我可以接受两列的时候卡片被缩短，但是第一张图片的那个卡片长度就是卡片极限
   长度了，**再长就要变成两列**。」
2. 「第二张图片所示，**完全错位了，所有的排版出现了问题**，一点都不够优雅流畅统一，观感很难受。」

⇒ ① 废弃七轮「中间带留白消不掉」的结论（那是保内容契约的**代价**，不是必须）；② 列数改由**上限**反解；
③ 新增一条硬要求：**档内统一**（同一档里所有卡的行数/高度/标签行必须一致，不许参差）。

## 二、八轮规则（取代第一节）

```
列数 n = 最小 n 使 (W − (n−1)×16) / n ≤ 793        # 超过 793 就加列 ⇒ 轨道铺满、零留白
卡宽   = n === 1 ? min(W, 793) : (W − (n−1)×16) / n
摘要行数 S = 一行放得下 35 字（floor((卡宽−69)/16.66) ≥ 35）? 1 : 2
理由行数 R = clamp(ceil(150 / floor((卡宽−69)/13.94)), 3, 7)
卡高   H = 288 + (S−1)×25 + (R−3)×23.7              # 卡底余量恒 27px（跨档同节奏）
标签槽位 T = clamp(floor((卡宽−69)/88), 2, 8)        # 余量折进 +N；永不换行 ⇒ 无半截 chip
```

**为什么「窄卡」不用截断兜**：七轮的实测已证 3 行只对卡宽 ≥766 成立（1600 档 72/837 被截）。
八轮把「卡变窄」的代价从「截断」改成「**加行 + 加高**」，内容契约因此在全档成立；
新增的代价是**卡高随档变化**（288→408），由 `--feed-card-h` 逐档下发，虚拟列表垫片同值。

摘要字号 f = clamp(内容宽 / ceil(35/行数), 0.81rem, 0.98rem)    # 第 1 行就够 ⇒ 1 行；不够 ⇒ 加行

- **门槛从 653 下移到 551**：0.98rem(16.66px) 时一行放 35 字要 `35×16.66+69 = 653px`；
  字号收到下限 0.81rem(13.77px) 时只要 `35×13.77+69 = 551px`。1400 档卡宽 556 落在门槛之上
  ⇒ 该档从 2 行槽位变 1 行槽位，**空白带归零**。
- **下限为什么 0.81 而不是 0.82**：0.82rem(13.94px) 时 35 字要 487.9px，而 1400 档内容宽实测
  **487.0px** —— 差 0.9px 就掉回 2 行。13.77px 只需 481.9px（余 5px）；它比理由字号(0.82rem)小 1%，
  肉眼不可辨。
- **卡高跟着字号走**（不是一律减 25）：H 的摘要项是 `S×(1.5×f)` ⇒ 1500 档 337→**310**、1400 档 360→**331**；
  **标准字号档与八轮那版逐像素等价**（S=1,R=3 ⇒ 191.91+24.99+71.1 = 288 ✓）。
- **档内统一**（〇块 14）：同档所有卡共享一组 (S, f, R, H, T)，逐档卡高实测只有 1 个值。
- 变量与真源：App 写 `--feed-summary-font`（px）/`--feed-summary-lines`/`--feed-reason-lines`/`--feed-card-h`；
  CSS 只消费（`.summary` 的 min/max-height 用 `em`，字号一变槽位高自己跟着变）。

## 五、十一轮追加（2026-09-30 第二次接续）—— 槽位垂直居中「真生效」（09-26 版是假阳性）

**验收失败实录**：十轮收口后栗子再报「卡片的异常空隙还是没解决」（红框＝理由文字与 ★ 行之间的空带，
2×793 宽档）。实测（`D:/tmp/gt-gap-chain.mjs`）：2 行理由卡到 ★ 行 **39.4px**（3 行卡 15.7px）——
09-26 甲A2/甲A3 的「垂直居中」**从未生效**。

**根因（两层叠加）**：
1. Chrome 早已把 `-webkit-box`（computed）**归一成 flow-root**（H-01 口径注 09-25 已记录这条引擎事实），
   而 09-26 的居中写在 `-webkit-box-pack: center` 上——box-pack 只作用于真 `-webkit-box` ⇒ **no-op**。
   （九轮的闸注记与十轮的修复各错开一层：闸知道 display 归一，却没拦住有人在同一元素上用 box-pack。）
2. 槽位（min-height＝R×23.7，按 150 字契约）与内容（p50 只占 2 行，793 档实测 33.2%）的差是结构性的
   （十轮追加 §二），空档必然存在——问题只在它**沉底**（读成「少了一行」）还是**摊匀**（读成内衬）。

**修复（外层管槽位+居中，内层管 clamp）**：
- `FeedCard.tsx`：summary/reason 文字包进 `<span class="clamp-text">`；
- `.reason-clamped` / `[data-sum-lines="2|3"] .summary`：外层 `display:flex; flex-direction:column;
  justify-content:center`（**真居中**：占满槽位的卡无位移，不满的摊成上下各半行）；
- `.clamp-text`：`-webkit-box + box-orient:vertical + line-clamp:var(--feed-*-lines) + overflow:hidden`
  （Chrome 归一后走现代 line-clamp，行为与旧版一致）；`text-wrap: balance` 随迁；
- G-11 媒体查询只留 `--feed-reason-lines: 2`（外层 clamp 已是死声明，删除）。

**量测口径修正（跟随架构）**：现代 line-clamp 把**被裁的行留在布局里**（`getClientRects`/Range 会数到
裁前行）⇒ 旧「boxH − textH」式空量在 clamp 卡上会读出假负值；`gittok-responsive-check.mjs` 的
rAll（scrollHeight>clientHeight 判截）、sumBlank（空带）、summaryLock/measure（clamp 读取）已改为
**内层 .clamp-text 上量**（S=1 的 clamp 仍在外层 base .summary，读数做内层优先、none 回退外层）。
⚠ 09-26 的「甲A2 已修待验收」与十轮回写的「理由槽位垂直居中（半做）」按本节改判：
**当时是假阳性（未生效），本轮才真生效**——状态标注纪律的教训：闸没断言过的「已修」一律当未修。

**验收读数（修复后）**：1920 档 2 行理由卡文本底→★行顶 **39.4 → ~23.7px**（其中 13.7px 是全卡一致的

# 十二轮追加（2026-10-01 第四次接续）—— 瀑布流重构：灵活优先，「别有空隙」唯一硬验收

> 栗子口径（块八，最高优先）：「卡片几行其实没有太大所谓，卡片多高其实也没有太大所谓，就是因为
> 宽度会变，所以其实定死没有意义，我的意思是**别有空隙**你懂吗」＋「足够灵活、足够优雅、足够统一、
> 足够流畅」。⇒ 价值排序＝**灵活 › 优雅 › 统一 › 流畅 › 其余**；十轮前的「档内等高 / 槽位 /
> 卡高算式」整族退场；三行满槽路线判废（理由契约 [100,150] 不变）；「别有空隙」＝唯一硬验收。

## 一、规则（四条，可直接复算）

1. **列数＝现行规则不变**：`feedColsForContentWidth`（卡宽 ∈ [460, 793] 的最小列数，n=1..3）原样。
   K>1 时启用**JS 列式瀑布流**（Chrome 153 实测不支持 `grid-template-rows: masonry`，探针
   `D:/tmp/gt-masonry-probe.mjs`：rowsValue "none"）；K=1（单列档与手机档）退化为普通单列堆叠，
   同一套代码（K 列容器的 K=1 特例）。
2. **卡高＝内容自然高度**：`.card` 定高（`--feed-card-h`）退场；`.summary`/`.reason-clamped` 的
   槽位（min/max-height）、clamp（`-webkit-line-clamp`）、槽内垂直居中（flex+justify-content:center）
   **全部退场**，文字自然流（摘要保留 `text-wrap: balance` 的行间配平与流式字号 0.98→0.81rem——
   它服务「一行读完 35 字」的可读性，与定高无关；摘要 S=1 的 nowrap+ellipsis 也退场，自然换行）。
   保留的唯一「定高」：`.card-tags` 26px（chip 单行 25.08px 自身填满它，不是死空间；配合 tagSlots
   预算防半截 chip，机制不变）。
3. **入列**：rank i → 列 **i % K**（轮转保近序：卡 i+1 不会跑到卡 i 上方远处）；列内自然堆叠
   （列距=行距，K 列等宽 `flex:1`）。备选（栗子目测若觉乱序）：最短列优先——代价 rank 序打乱更狠。
4. **虚拟化＝列内累计偏移**：每列维护高度数组 → 前缀和 `prefix_c` → 滚动窗口对每列**二分**找
   `[scrollTop − overscanPx, scrollTop + viewportH + overscanPx]` 交叠的卡区间（overscan=
   `FEED_OVERSCAN_ROWS × rowH` px，语义仍≈3 屏）；每列 topPad/bottomPad 独立。高度来源：
   **测量优先、估算兜底**——渲染后 rAF 读 `offsetHeight` 入缓存（键=repo，代际=卡宽取整，
   宽度变了全量换代）；未测量卡用 `estCardHeight(card, cardW)` 估算（固定件 + 摘要行数×行高 +
   理由行数×行高，行数=ceil(字数/每行容量)，可复算纯函数）。测量值与列偏移差 ⇒ 同帧重算一次列
   偏移（带守卫防循环）。
