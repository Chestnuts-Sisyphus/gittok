# 分区体系 v3 · 决策记录（2026-09-14 晚）

> 立项缘由：栗子 2026-09-14 原话——
> 「有一些 skill 出现在资源区……**问题不在于一个小小的项目分类失败，而在于分类体系本身，
> 没做到精准划分**」。
> 经核对，症状成立但不是孤例；真缺陷在体系：四区枚举里 3 个是「交互方式」、1 个是「技术题材」，
> 两个维度混排 → 数学上不可能互斥划分 → 工具区成兜底漏斗。
>
> **栗子的裁决（本轮拍板，原话要点）**：四个分区**确定不推翻**（AI / 资源 / 工具 / 创意 就是这四个），
> 诉求是「让分区边界清晰、二分明确」；「工具作为兜底，没问题，但前提是工具里的任何一个项目
> 拉出来都不可能成为其他三个分区的内容」；「另外工具区确实占比较大，那就涉及到其他三个分区的
> 边界是否过小、是否不够清晰、是否不够合理的问题」。
>
> 因此 v3 **不改枚举、只改判定结构**：把四区判定从「四条并列描述」改成**三分支二分链**。

## 一、v2.2 的缺陷（已实测证据）

| 项 | 实测 |
|---|---|
| 判定链原文 | 资源=「人拿它是学/看」；创意=「人拿它是玩/创作」；工具=「人拿它干活」← **都是交互方式**；AI=「它靠智能干活」← **技术题材** |
| 兜底率 | 工具区 1206/2477 = **48.7%**（擦 60% 均衡线） |
| 工具区污染 | 其中 **402 张（33.3%）** 描述里明确带 AI/模型/Agent 关键词 |
| 多类同时命中 | AI 区里 329 张 funScore ≥ 0.5（既「靠智能干活」又「好玩」）、300 张带「实用/工具」气质标签 |
| 结论 | 两个维度混在一个枚举里 → **不可能互斥划分**；「skill 进资源区」只是这个缺陷的一个可见症状 |

判定链文本原来的四句话，任意两句都不构成排他关系（「学/看」与「干活」在教程类项目上直接冲突，
「玩/创作」与「干活」在创作工具上直接冲突）。

## 二、v3 体系：三分支二分链

判定按顺序问三个**能用是/否回答**的问题，**第一个答「是」的就是结果**，三问全否 = 工具。

| 问 | 问题 | 答「是」→ |
|---|---|---|
| 问 1 | 它是**「作品」**吗？——人拿它是为了玩 / 看 / 听 / 自己动手创作（终局价值是体验或表达） | **创意** |
| 问 2 | 它是**「读物」**吗？——不安装、不运行它，只读或下载它的内容就能拿到全部价值 | **资源** |
| 问 3 | 它是**「智能本体」**吗？——把 AI / 模型能力整体拿掉，它什么都不剩 | **AI** |
| — | 三问全否 | **工具**（兜底） |

每一问在 prompt 里都带「判据 + **不算「是」的情况**」两段（定义文本唯一源：
`src/feed/taxonomy.ts` 的 `ZONE_BRANCHES` / `ZONE_RULES_V3`，生产 prompt、回填脚本、验收脚本共用同一份）。

### 互斥性（构造性，不是抽查结论）

- 进入某区的条件 = **前面所有分支都答「否」 + 本分支答「是」**；
- 工具区的条件 = **三问全否**；
- 所以工具区的卡在**定义上**不可能属于其余三区——这正是栗子要的「工具里的任何项目拉出来都不可能成为其他三区的内容」；
- 其余三区之间同样互斥：落点是「第一个答是」的分支，前面每一问都已经答否。

这不是「抽查 100 张看起来还行」，而是结构保证；`scripts/gittok-zone-orthogonality.ts` 会对
二分链结构本身做断言（分支数 = 区数−1、落点互不重复、兜底区没有自己的「是」分支、每支都有边界反例）。

### 判例集（边界钉死，写进体系与验证脚本）

| 案例 | 判定 | 依据 |
|---|---|---|
| 给 AI 编程助手用的技能包（skill） | **AI** | 拿掉 AI 助手什么都不剩 → 问 3 答是（**栗子点名的那个错分，在此闭死**） |
| 解读 AI 的教程 / 论文清单 / 提示词大全 | **资源** | 读物，不运行就拿全部价值 → 问 2 答是（题材带 AI ≠ 它是智能本体） |
| AI 绘画工作台（ComfyUI 一类） | **创意** | 人拿它创作，终局价值是作品 → 问 1 答是 |
| AI Agent 框架 / 推理引擎 / 向量检索骨架 | **AI** | 智能本体，拿掉模型什么都不剩 → 问 3 答是 |
| 游戏引擎 / 游戏开发框架 | **工具** | 给开发者干活用、不是给人玩的作品（问 1 否）；不跑模型（问 3 否） |
| 带 AI 摘要的自托管笔记 | **工具** | AI 只是加的一个功能，拿掉照常跑 → 三问全否 |

## 三、其他三区是否「过小 / 不清晰 / 不合理」（栗子点名的第二问）

判据：看**重判后**的分布与边界案例命中情况（数字见 §五）。
设计上三区各有明确入口条件（作品 / 读物 / 智能本体），且都属于「必要条件成立才能进」——
即三区不是「剩下的东西」，而是「答是才进」；工具区吃的是「三问全否」的真正兜底。

需要观察的两个风险（诚实标注）：
1. **资源区可能偏小**：读物类项目在 GitHub 上的绝对量本身就少（v2.2 也才 230 张 / 9.3%）。
   如果重判后仍显著偏小，说明的不是「边界不清」，而是**语料结构如此**——这条要在验收里如实报出来，
   不能靠放宽判据把数字凑大。
2. **创意区的边界**（「作品」vs「给开发者做作品的框架」）是最容易飘的一支：判例已把
   游戏引擎一类的反例写进 prompt，重判后用抽样人工核对确认。

## 四、与 v2.2 的迁移关系（A3 / A4 的处置）

- **A3（四处耦合）**：zone 词表与旧 category 映射收敛到 `src/feed/taxonomy.ts` 一处；
  前端 `web/src/channels-axes.ts` 的 tab 词表、`src/feed/channels.ts`、生产 prompt、回填脚本
  全部 import 同一份，不再各写一份。
- **A4（zoneToCategory 反向映射语义丢失）**：v3 里这条**不再成立**——四区枚举没变，
  `category ↔ zone` 是 **4↔4 双射**（ai↔AI / learning↔资源 / tool↔工具 / fun↔创意），
  往返无损。正交性脚本对「双射性」加了断言；同时新增 `legacyZone` 字段承载旧值，
  于是不再需要用「把新 zone 压回旧 category」来表达新语义。
- **旧值不丢**：重判前把 v2.2 的 zone/funScore 存进 `legacyZone` / `legacyFunScore`，
  供对照与回滚；两者都不参与任何排序。

## 六、关键假设（未说明处的推测执行，栗子扫一眼即可纠偏）

1. **顺序 = 优先级**：把「创意」放第一问，意味着「AI 绘画工作台」判创意而不是 AI。
   依据是 GitTok 的读者是普通网友、分区回答的是「人拿它干什么」——创作/娱乐优先于技术题材。
   若栗子认为 AI 题材应当优先，把 `ZONE_BRANCHES` 的顺序调一下即可（判例集同步改两处）。
2. **游戏引擎/开发框架 = 工具**（不是创意）：按「给人玩的作品」与「给开发者干活的框架」分开。
3. **AI 教程/清单 = 资源**（不是 AI）：题材不加权。
4. 「工具区兜底」保留：栗子明确认可，前提是排他性由构造保证（见 §二）。
